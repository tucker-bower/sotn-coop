# M0 design: test harness, 8MB verification, disc builder skeleton

**Status:** approved by Tucker on 2026-10-18 (SwanStation primary; Docker deferred, D14).
**Budget:** 12% of the month. Spike so far: about half a day.

## Goal
Give the agent a fast, headless, deterministic way to run the game. Make sure every later milestone can be verified by scripts, not by eye. Also prove that the riskiest platform assumptions hold (8MB mode, disc rebuild).

## What the spike already proved
| Question | Result |
|---|---|
| Can we rebuild a bootable *modified* disc? | **Yes.** `make disk_debug` rebuilds the image with the project's debug module injected. It boots to the title screen. |
| Can we run it headless and fast? | **Yes.** SwanStation libretro core, driven from Python via `libretro.py`: about **200 fps (3.5× real time)** on one CPU. |
| 8MB mode? | **Yes.** Exposed RAM is 8MB with the core option on. |
| Do we need a copyrighted BIOS for testing? | **No.** OpenBIOS (open source, from PCSX-Redux) works in fast-boot mode. Players will still use their own BIOS dump. |
| Deterministic? | **Yes.** Two identical 40-second runs gave identical RAM hashes at every checkpoint. |
| Prior art for running code in 8MB? | **Yes.** The project's debug module sets the RAM_SIZE register, copies itself to `0x80280000`, and hooks the main loop. That's exactly our pattern. |

|---|---|---|---|

## Proposed design

### 1. Harness (`mods/co-op/harness/`, Python)
- `emu.py`: a thin wrapper around the SwanStation core. It provides `step(n, pad1, pad2)`, `save_state()`, `load_state()`, `read(symbol)` and `screenshot()`. Symbol addresses come from the decomp's map files, so RAM reads are by name (`g_Player.unk0C`) rather than by address.
- `scenario.py`: declarative test scenarios: a starting savestate, an input script or bot, and assertions over time ("P2 posX changes", "room ID == 0x12 by frame 600", "no entity slot corruption").
- `lockstep.py`: runs two instances with identical inputs and compares RAM every N frames. This stands in for netplay desync.
- `bots/`: simple scripted bots (walk right, follow P1, mash attack). Calls to a small LLM are optional and come later, only when needed.
- Output: a JSON report plus a short GIF per scenario, for PR evidence.

### 2. Savestate library
Generating savestates needs a one-time pass through the intro: title → new game → name entry → prologue → castle entrance. I'll script that with inputs and save states at key points: entrance, Alchemy Lab, Marble Gallery, the first boss doors. Savestates contain game RAM, so they're **git-ignored, never committed**. They're regenerated by a script from the user's own disc.

### 3. Co-op module skeleton (8MB)
Copy the debug module's proven pattern into `mods/co-op/module/`:
- Linked at a fixed address in the 8MB area.
- Sets RAM_SIZE, then hooks the per-frame loop.
- For M0 it does nothing but write a heartbeat counter, which the harness asserts on.

**Open choice for M1:** loading through the familiar slot (as the debug module does, which costs a familiar) versus a small hook compiled into DRA. Since we build DRA from source, the DRA hook is cleaner. I recommend deciding that in the M1 design doc.

### 4. Disc builder (D9), skeleton only in M0
`mods/co-op/docker/`, modeled on the Maria mod: `docker run -v ./disks:/disks <image>` takes `sotn.us.cue/bin` and outputs `sotn_coop.us.cue/bin`. In M0 it only produces the heartbeat build. It gets polished in M5.

### 5. Bootstrap script
`mods/co-op/scripts/bootstrap.sh` handles the toolchain, Go module mirrors (needed in the cloud sandbox), the matching build, and the SwanStation and OpenBIOS builds. That makes the environment reproducible in a fresh session, or on your PC under WSL2.

## Acceptance criteria
1. `bootstrap.sh` on a fresh machine plus the user's disc yields a matching build and a working harness.
2. A scripted intro produces savestates at the castle entrance and 3 later locations.
3. A scenario walks Alucard through 3 entrance rooms, with assertions on room ID and position.
4. The heartbeat module runs in 8MB on SwanStation (harness assertion). It also boots on DuckStation and PCSX-Redux on Tucker's PC (one manual check each, or via computer use).
5. The lockstep check passes for 10 minutes of scripted play.
6. A script builds the heartbeat disc from a user-supplied image. Docker is deferred to M5 (D14).

## Risks
- **The intro takes a long time to script** (name entry, prologue). Mitigation: an RAM-poke shortcut that's allowed in the harness only.
- **libretro.py quirks.** One bug (NULL frames) is already patched in our wrapper. Fallback: a ~200-line C frontend.
- **OpenBIOS vs. a real BIOS** might differ in edge cases. Mitigation: at milestones, Tucker runs one smoke test on a real BIOS.

**Findings that change M1:**
- **The familiar slot only loads while a familiar is active** (`g_Servant != 0`), and `TT_000` is the Bat. The debug-module pattern can't run co-op code from a new game. The harness turns the Bat Card on to test it. M1 needs a real loader. Other overlays hardcode only 2 DRA addresses, so a hook relinked into DRA is feasible. The M1 design will propose options.
- **Patched code needs `FlushCache()`.** Without it, PCSX-Redux (dynarec) never runs the hook, and real hardware's instruction cache wouldn't either. SwanStation hid the bug. The upstream debug module has the same latent bug.
- **Savestates are per disc image.** The library is keyed by disc.
- Skipping the prologue counts as "Richter took no damage", which gives Alucard +1 to all stats, a real game path. Harness only.
